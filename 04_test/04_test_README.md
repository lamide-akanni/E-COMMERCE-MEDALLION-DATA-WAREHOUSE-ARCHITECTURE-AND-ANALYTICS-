# Testing

Four scripts, covering three different kinds of check. Run them in this order after any change to
the pipeline.

| Script | Checks | When to run |
|---|---|---|
| `quality_checks_silver.sql` | Did the bronze to silver transformation do what it claims? | After every silver load |
| `quality_checks_gold.sql` | Is the star schema sound and do the joins resolve? | Before loading the reporting model |
| `pipeline_tests.sql` | Does orchestration log correctly, and does a failure reach Slack? | After any change to a load procedure, the batch file, or the alerting |
| `gold_views_check.sql` | Print every gold view definition for lineage review | When reviewing or handing over the model |

## How to read the results

Most queries are written so that **zero rows means pass**. A non-empty result is a failure that
needs investigating before the layer above is trusted. Queries that return figures for review rather
than pass or fail are marked informational in the script.

Each check prints its own name before running, so when the whole file is executed you can tell which
check produced output.

## What the silver checks cover

Nine tables, grouped by source.

**Structural.** Duplicate or null primary keys after deduplication. Untrimmed text. Grain violations
where more than one row exists per declared key combination.

**Standardisation.** Every decoded column is checked against its expected value set. Finding `M`
where `Male` should be, or `DE` where `Germany` should be, means the CASE expression in the load
procedure did not fire.

**Business rules.** Sales amount reconciled against quantity times price. Negative stock. Non-positive
exchange rates. Order dates later than shipping dates.

**The date rebase.** Two checks confirm the twelve year shift ran: sales should span 2022 to 2026 and
products 2015 to 2025. Dates in the 2010s mean the shift did not apply, which would put transactions
outside the range of `dim_date` and silently lose them to a blank date bucket downstream.

**Known exceptions.** The null order date check expects exactly 19 nulls out of 60,398. That is the
documented source defect, not a regression. A different number means something changed.

## What the gold checks cover

**Surrogate key uniqueness.** Every dimension key, plus `full_date` as the alternate key on
`dim_date`, plus `event_id` on `fact_web_events`.

**Referential integrity.** A null surrogate key in a fact means the join in the gold view failed to
find a match. Checked for every foreign key on every fact.

`fact_web_events` is the exception. Nulls there are expected and correct: anonymous sessions carry no
customer, and a homepage view carries no product. That check is informational and reports the
proportion rather than failing.

**Grain.** Each fact is grouped by its declared grain and checked for duplicates. `fact_sales` by
order number and product key. `fact_inventory` by product, warehouse and date. `fact_fx_rates` by
date and currency pair.

**Calendar integrity.** `dim_date` is generated by a recursive CTE, so the row count is checked
against the actual number of days between the boundary dates, and `date_key` is checked against
`full_date` on every row.

**Security coverage.** Every country in `dim_security` is checked against `dim_customers`. A grant
pointing at a country with no customers means that user opens the report and sees nothing.

## What the pipeline tests cover

Three sections, and the third is the one that matters.

**Section 1 confirms the objects exist.** The full inventory should return 37 objects across four
schemas. There is also a check that queries `sys.sql_modules` for every load procedure and reports
whether its definition contains `THROW`. Every row must read yes. A procedure whose CATCH block
prints and returns normally looks like success to `dbo.log_and_run`, so the failure is recorded as a
pass.

**Section 2 runs the pipeline and reads the log.** Six steps, all SUCCESS, grouped under one
`run_id`. There are also two queries for operational use: run history across the last ten runs, and
average duration per step, which is where you would notice a step slowing down over time.

**Section 3 deliberately breaks it.** This is the important one.

An error has to survive four handoffs to reach a human:

```
INSERT fails → stored procedure → sqlcmd → batch file → Slack
```

Each handoff can drop it silently:

- A `CATCH` block that prints and returns normally looks like success to the caller. Every load
  procedure therefore ends its `CATCH` with `THROW;`.
- `sqlcmd` exits 0 by default even when the T-SQL failed. It reports that the batch was sent, not
  that it worked. The `-b` flag makes it exit non-zero on error.
- Batch files need `if %errorlevel% neq 0`, not the older `if errorlevel 1` form.

Fixing only one of these changes nothing. All three are required.

The test renames `silver.inventory` so that `silver.load_slv_inventory` cannot find its target, runs
the pipeline, and confirms a FAILED row appears in `dbo.etl_log` with the error message attached.
Then it renames the table back and re-runs to confirm recovery.

**Run it from the command line, not SSMS.** `EXEC dbo.run_full_pipeline` from SSMS only tests the
SQL half. It never reaches the batch file or Slack, so it cannot tell you whether the alert fires.
Running `run_pipeline.bat` tests the whole chain.

## Results from the last full test

| Test | Expected | Observed |
|---|---|---|
| Object inventory | 37 objects | 37 |
| Successful run | 6 steps, all SUCCESS | 6, all SUCCESS |
| Failed run, `etl_log` | `silver.load_slv_inventory` = FAILED | FAILED, error 4701 |
| Failed run, Slack | Message reading FAILED at SQL Pipeline | Received |
| Recovery run | 6 steps back to SUCCESS | 6, all SUCCESS |
| Recovery run, Slack | Message reading SUCCESS | Received |

Before the `THROW`, `-b` and `%errorlevel%` fixes were applied, the same broken run logged SUCCESS
and posted a green Slack message. That is the failure mode these tests exist to catch.

## What is not covered

**Row-level security.** Tested manually in Power BI using View as, for both a scoped user and the
global user. There is no automated test, because RLS is enforced by the reporting model rather than
the database.

**Python ingestion.** `fetch_fx_rates.py` and `generate_web_events.py` have no unit tests. Their
output is validated indirectly by the silver checks on `fx_rates` and `web_events`.

**Incremental correctness.** Every load is a full truncate and insert, so there is no incremental
logic to test. This changes if watermark-based loading is added.
